Search URL construction

searchMovies starts its path with /, while the shared helper concatenates the base URL and path. This can produce /3//search/movie; use a relative path or URI resolution to avoid the doubled slash.

Optional genre parameters

The list and search helpers interpolate optional withGenres directly into the URL. If omitted, the current request contains with_genres=null.

Query encoding

Query values are assembled through string interpolation. Values containing spaces or reserved characters should be URI-encoded when constructing requests.

Response handling

All requests use GET through getMethod. fetchMovies and searchMovies explicitly check for status 200; other helpers parse the response body without a shared status check.

Search movie upload

Full-detail review and uploads inside Import

Choose Import > Search API, search a title, select result checkboxes, and click Fetch selected details. Each search result shows a poster thumbnail beside its checkbox, with a placeholder when the poster is missing or cannot load. Search results provide TMDB IDs only; their sparse metadata is never used as an Appwrite payload. Complete movie details and credits are fetched into the inline review queue, without writing database rows or opening another route. Search language controls discovery; detail and profile requests use en-US.

The inline queue uses the same BulkMovieImportWorkspace and BulkMovieImportController as the standalone bulk screen. Set franchise beside the search title field (blank writes null); it is the shared upload default, not a TMDB search filter. Set cast/crew unique-person counts (15 each by default), and whether to include people/credits. Review and edit movie fields or override settings per movie, then explicitly confirm Upload selected. Result checkboxes choose IDs to fetch; queue checkboxes choose fetched movies to upload.

Uploads use the current movies, genres, people, movie_cast and movie_crew tables: three movie workers share one pool of 15 people. Existing profiles are reused, missing profiles are coordinated across movies, genre writes never upsert inverse relationships, and readback verifies stored values. Failed detail fetches and unfinished uploads have separate retry actions; successful work is kept, with per-movie and per-person statuses.

New searches, page changes, and clearing discovery results keep the review queue, settings, edits and retry state. Switching API modes keeps the queue but hides it in Movie list mode. Removing a queue item or clearing the queue requires confirmation; no Appwrite rows are deleted. Active work or dialogs block search/source changes and navigation. Leaving Import with a queue warns about local state; navigation tabs retain it during the app session, but closing/restarting the app loses it. Cancel requests finish in flight.

Movie list API is browse-only. Its obsolete upload action is disabled because the legacy table was removed. Use Search API, Movie ID editor, or Bulk movie upload for current-schema ingestion. The legacy sparse uploader has been removed; no importer recreates the deleted table.

Movie ID editor

Independent Movie Info and People Info tabs

Open Import > Movie ID editor. Enter any positive TMDB movie ID to fetch movie/{id}?append_to_response=credits&language=en-US. Movie Info shows all database movie fields in editable text fields, including genres as a JSON array of ID/name objects and optional franchise (blank writes null). Additional TMDB response fields, including the complete credit response, appear in read-only text fields; they have no matching database columns and are not uploaded. Fetching another movie replaces the editor; failed fetches keep the prior movie explicitly labeled with its own ID. Changes remain in the editor across tab switches.

Movie Info upload validates edited fields, ensures genres exist first and the edited movie second, and verifies the written fields by readback. It does not upload profiles or credits. Invalid numbers, dates, booleans, genre JSON, and required values report explicit errors; optional text truncation warnings remain visible. The MCU importer and standalone bulk importer remain available; Search API now uses the shared inline full-detail workflow described above.

People Info has separate unique cast and crew lists. Select checkboxes or enter independent counts (default 15; 0 clears a group). Cast is ranked by TMDB order; crew follows response order. All roles/jobs in selected sections are retained. Search filters visible people without altering selection; count selection uses the full list. A person selected in both groups is processed once, with shared status in both lists.

People upload requires the fetched movie ID to already exist in Appwrite. It never implicitly uploads the movie or uses unsaved movie edits. Each of at most fifteen parallel workers checks the person, fetches and creates a full profile only when missing, then upserts and verifies that person's selected credits. Existing profiles are never overwritten. Stable TMDB credit IDs and legacy-duplicate checks make retries safe. Credits are grouped by person once and rendered lazily to avoid repeated full-list scans and eager list widgets.

List statuses are Not uploaded, Uploading, Success, Failed, Already Exists. Already Exists means the profile was reused and selected credits were verified. A profile whose credit upload fails is Failed with a partial-write message, not successful. Retry selected failed people without re-uploading successful ones. A shared permission/schema/rate-limit failure stops scheduling new workers while in-flight workers settle. Cancellation keeps stored rows; no destructive rollback occurs. This screen uses the same temporary anonymous permissions and actual Appwrite table IDs described below; it never creates schema or grants permissions.

Bulk movie upload

Multi-ID previews and bounded batch uploads

Open Import > Bulk movie upload. Paste positive TMDB movie IDs separated by commas, spaces, semicolons, or newlines. IDs are validated and deduplicated before fetching. Up to three movie requests run concurrently. Adding IDs preserves already fetched movies, their edits, and upload progress; failed fetches can be retried independently. Preview cards show title, poster, release date, selection, and status.

Set shared franchise (blank writes null), cast/crew unique-person counts (default 15 each; zero skips a section), and whether to include people/credits. Edit / override settings opens the supported movie fields, including genre JSON, and optional per-movie counts, franchise, and upload mode. Saving edits creates a new local upload plan without deleting stored rows. Conflicting names for one shared genre ID in a batch are reported before writes.

One upload action processes at most three movies at a time. All movie workers share a single 15-person pool, not 15 per movie. Each movie ensures genres exist and verifies its movie row before uploading selected profiles and credits. All jobs/roles for selected unique people are kept. Genre writes reuse the safe read/create/name-only update service; movie writes retain strict unique-link verification and duplicate-link repair.

Concurrent movies share a single in-flight profile operation per person ID. Existing profiles are reused without fetching or overwriting; missing profiles are fetched, created, and verified once per batch. Genre writes are also shared by ID/name. Profile/credit failures are visible inside each movie's people statuses. TMDB uses bounded retries and Retry-After; exhausted rate limits and shared permission/schema failures pause new work while in-flight work settles.

Movie statuses are Queued, Fetching, Ready, Uploading, Success, Partial, Failed. Retry selected unfinished movies retains the original mapped data/settings and skips verified genre rows, movie rows, people, and credits. Changing shared defaults does not change a previous retry plan; edit that movie to start a new plan. Successful movies are excluded from upload until edited. Progress and edits live in memory while the screen is open, not across app restarts. Cancellation preserves completed rows. This is an anonymous client importer, not a background server job; keep the screen open until it finishes and revoke temporary public writes afterwards. Existing single-movie and MCU screens remain available.

MCU import

Separate screen, full-schema ingestion

Open Import > MCU import. Select from the 22 actual results in MoviesRepo.marvelMovies; seed titles/posters are previews, not the source of uploaded movie details. Franchise is user-entered and optional: blank stores null (and clears a previous value on refresh); enter mcu or another value if desired. The column must be optional and sized for the entered value.

Cast and crew limits default to 15 unique people each, per movie; 0 skips that group. Cast people are chosen by ascending TMDB order, crew by TMDB response order. All roles/jobs for chosen people are retained, including later credits, so credit row counts can exceed the limits. A person selected for both groups is created only once. Previously stored credits outside the selected import are kept with warnings, not deleted.

Requests use ApiConstants.apiKey, JSON headers, and no body. Movie groups are processed sequentially; person fetching uses at most three workers. TMDB requests time out after 30 seconds and make at most three attempts for transport failures, 429, or 5xx. Retry-After is honored up to two minutes; longer waits stop the item with a retry-later error. Permanent failures and malformed responses are visible.

Upload order: genres + people, then movies with native genre links, then movie_cast + movie_crew. Movies, genres, and people use TMDB IDs as row IDs; credits use stable TMDB credit_id values. Different roles/jobs are retained. Movies use create/update; selected credits use upserts. Genres are checked by TMDB row ID, created only when missing, and updated only if their name changes. Genre updates send only the name, never the inverse movies relationship; unchanged genres are read and verified without writes. This avoids genre upserts replaying existing movie links and duplicating relationships on other movies. People are checked by TMDB row ID before enrichment and created only if missing; a concurrent-create conflict reuses the existing row without overwriting it. Permission/network failures are not treated as missing people. Readback checks newly created profiles and supplied movie/credit fields and relationship IDs. Movie writes use create/update rather than relationship upsert: unchanged genre sets are omitted from updates, and supplied genre IDs are unique. Readback rejects duplicate genre links instead of hiding them with a set comparison. If an existing movie has duplicate genre links, the importer clears only those links and restores the intended unique IDs; genre rows and cast/crew links are not deleted. This repair uses two updates, not an atomic transaction: a network failure can leave a partial relationship update, which is reported and can be repaired by retrying with the intended genres. Avoid concurrent imports of the same movie. Missing required data/invalid dates fail explicitly. Overlong optional prose/aliases are truncated with field-specific warnings; IDs, dates, URLs, and image paths are never silently shortened. Null optional dates are preserved; real dates become UTC ISO 8601 midnight. Only relative image paths are stored.

Temporary anonymous access: administrator setup

No login, anonymous session creation, Account API, or server API key is used. In Appwrite, manually allow Any create, read, and update on all five tables, enable the database/tables, and register the application's hostname. Existing rows must permit read/update where row security is enabled. Read permission alone is not sufficient for upserts. No delete permission is needed. Anyone can insert or modify this public data, not just this screen. Remove temporary Any create/update grants after importing, including any per-row public grants you configured. Use proper authorization before production.

The client SDK cannot inspect column metadata. Preflight checks anonymous table reads and relationship selections, not write grants or schema availability. Confirm that franchise is an optional writable String sized for the entered value and that all expected attributes exist. Check integer storage supports revenue/budget above 2147483647; the screen reports actual write/schema errors instead of changing columns or permissions. Appwrite transport/5xx failures get bounded retries; SDK 429 stops the run because Retry-After is not exposed. In-flight writes finish on cancel; new operations stop, and stored rows remain.

Start with one movie, inspect its fully verified result, then select the remaining movies. Retry unfinished imports safely. Matching legacy credits with random IDs block a movie with a migration warning rather than creating duplicates. Stale credits are kept with warnings; no destructive synchronization or rollback is performed. The screen reports partial writes, field warnings, and per-table verified counts. Successful rows are never deleted. No reviews, recommendations, videos, extra images, unrelated filmography, or new MCU discovery are fetched.

Import mappings validate raw JSON at the boundary instead of reusing browsing DTO parsers that lose absent-versus-null fields. Browsing models/helpers remain unchanged.
